# Офісний тест: базова станція, дві камери, оператор

Інструкція для Windows. Базова станція запускає сервер, а оператор користується
браузером на іншому комп’ютері. Наявність OpenAI API не потрібна для першої
перевірки відео, подій і запису.

## 1. З’єднання

```text
Камера 1 ─── LAN ────────────────────┐
Камера 2 ─── HT-HD01 ≈≈ HT-HD01 ────┼── комутатор/офісний роутер
Базовий ПК ─── LAN ─────────────────┤
ПК оператора ─── LAN або офісний Wi-Fi ┘
```

Використовуйте звичайну офісну мережу, без гостьової ізоляції клієнтів. Камери
живляться окремо згідно зі своїм паспортом. Для DS-2CD2D25G1/M-D/NF плануємо
12 В; з’єднання Ethernet саме по собі живлення не забезпечує.

Пара Heltec має передавати мережевий трафік у режимі моста. Якщо вже перевірена
конфігурація працює, не скидайте її. Справжній mesh або інший радіоканал теж
можна використати, якщо базовий ПК має доступ до RTSP другої камери. Програма
не залежить від кількості радіопереходів. Не з’єднуйте кінці того самого моста
ще й паралельним кабелем: для цього тесту резервна петля не потрібна.

Найпростіше мати всі вузли в одній IP-підмережі. З’ясуйте поточні адреси;
не призначайте довільні адреси в зайнятій офісній мережі. Потрібні IP базового
ПК та обох камер. Паролі зберігайте локально, не надсилайте в чат.

## 2. Перевірка камер із базового ПК

Відкрийте вебінтерфейс кожної камери, перевірте час, активацію та облікові дані.
Для стартового тесту можна задати H.264, 1920×1080, 10–15 кадрів/с, близько
2 Мбіт/с на камеру. Це початкові параметри тесту, а не гарантований оптимум.

Типовий основний потік Hikvision:

```text
rtsp://LOGIN:PASSWORD@CAMERA_IP:554/Streaming/Channels/101
```

В обох окремих камерах використовується 101, не 201 у другій. Якщо RTSP-порт
змінений, використовуйте фактичний. Перевірте кожен потік у VLC: «Медіа» →
«Відкрити мережевий потік». Це додаткова перевірка; VLC не потрібен серверу.
Символи `@`, `#`, `:`, `/`, `%` у логіні/паролі всередині URL потрібно
URL-кодувати. Пароль камери через це змінювати не потрібно.

## 3. Підготовка базового ПК

Якщо це поточний комп’ютер розробки, залежності вже встановлені. Якщо інший —
розпакуйте `varta-office.zip` у постійну папку, наприклад `C:\Varta`, та встановіть
Python 3.12 (64-bit). У PowerShell відкрийте папку й виконайте:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
```

Інтернет потрібен для встановлення залежностей. Node.js не потрібен: у ZIP
панель уже зібрана в `dist`. Віртуальне оточення .venv з іншого ПК не копіюйте.

Створіть копії конфігурації (якщо такі файли вже є, спочатку збережіть їх):

```powershell
Copy-Item config.office.json config.local.json
Copy-Item .env.example .env
notepad .env
```

У `.env` задайте реальні значення:

```text
VARTA_CAM1_RTSP=rtsp://LOGIN:PASSWORD@CAMERA_1_IP:554/Streaming/Channels/101
VARTA_CAM2_RTSP=rtsp://LOGIN:PASSWORD@CAMERA_2_IP:554/Streaming/Channels/101
VARTA_OPERATOR_TOKEN=YOUR_OWN_LONG_OPERATOR_PASSWORD
```

Це шаблони, не готові адреси чи пароль. Пароль оператора придумайте окремий,
щонайменше 16 символів. `VARTA_CAM3_RTSP` і `OPENAI_API_KEY` поки лишіть порожніми.
Профіль office вже вимикає деморежим, вмикає запис і містить рівно дві камери.

Якщо сервер уже запущений, зупиніть його Ctrl+C. Запустіть із доступом по LAN:

```powershell
.\.venv\Scripts\python.exe -m backend --lan
```

Вікно сервера тримайте відкритим. На базовому ПК відкрийте
http://127.0.0.1:8765, увійдіть із паролем оператора й перевірте обидва кадри.

## 4. Комп’ютер оператора

Відкрийте `http://IP_БАЗОВОГО_ПК:8765` і введіть пароль оператора. На цьому ПК
встановлювати Python, копіювати програму або зберігати паролі камер не потрібно.

Якщо локально панель працює, а з оператора ні, перевірте профіль мережі Windows,
ізоляцію Wi-Fi та дозвіл TCP 8765 у брандмауері базового ПК. Потрібен дозвіл
лише від локальної мережі/ПК оператора, не вимкнення брандмауера. У керованій
офісній мережі це правило додає адміністратор. Порти в інтернет не переадресовуйте.

На базовому ПК вимкніть автоматичний сон на час тесту. Якщо ноутбук — лишіть
кришку відкритою або налаштуйте її закриття так, щоб сервер не засинав.
Потрібно понад 5 ГБ вільного місця; для тесту зручніше мати не менше 20 ГБ.

## 5. Перевірка на 20–30 хвилин

1. Обидва кадри змінюються, панель не показує «Демонстраційний режим».
2. Статус запису показує 2/2. У панелі огляд — 1 кадр/с, це очікувано.
3. Порухайтеся перед кожною камерою кілька секунд; має з’явитися подія зміни
   кадру. Пауза між такими подіями в офісному профілі — 15 секунд.
4. Відкрийте подію, перевірте кадр і позначте її переглянутою.
5. Тимчасово від’єднайте тільки мережеве підключення другої камери або її
   радіоміст. Має з’явитися втрата зв’язку, а запис першої камери продовжитися.
   Поверніть підключення: дочекайтеся кадру й події відновлення (може знадобитися
   близько 30 секунд). Не відключайте загальний офісний роутер.
6. Закрийте браузер оператора на хвилину та відкрийте знову: сервер має
   продовжувати запис. Відкрийте «Журнал», оберіть період 8 годин.
7. Через 4–5 хвилин після початку запису відкрийте заново вкладку «Журнал»,
   завантажте завершений MKV-фрагмент і перевірте відтворення.

У журналі максимум 300 подій за вибраний період; огляд показує останню годину.
Простий детектор може реагувати на тіні/освітлення: це не класифікатор людей.

## 6. Додавання хмарного аналізу

Коли локальні перевірки пройшли, додайте `OPENAI_API_KEY` у `.env`, змініть
`cloud_enabled` на `true` у `config.local.json` і перезапустіть сервер.
API оплачується окремо. Для першої перевірки згенеруйте нову подію; старі
локальні події автоматично не відправляються. Подія має отримати позначку
«Опис ШІ». До цього чат повертає лише локальну вибірку журналу.

У хмару передаватимуться вибрані кадри подій та текст журналу для запитань.
Виберіть тестовий ракурс без офісних документів і моніторів із робочими даними.
